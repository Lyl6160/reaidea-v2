## Authority distinction

- `architecture/VISUAL_AUTHORITY_REGISTER.md` identifies approved composition references and runtime image layers.
- A Visual Page Blueprint approves one exact page/state, wording, controls, interactions, responsive images and protected plumbing.
- A flattened composition image is not production UI and its illustrative sample state is not runtime truth.
- A daily screenshot is evidence, not authority, unless the founder explicitly approves an exact version and it is registered with path/hash.

## Visual-first rule

Founder direction → REV finished screen design → founder approval → registered Visual Page Blueprint → exact contract → implementation → measured verification → checkpoint commit.

One screen/state proceeds at a time. No agent may alter production presentation because a chat description “seems clear,” because an adjacent screen was approved or because implementation already exists.

## Asset rule

- Reference canonical images at their existing repository paths.
- Do not copy large Home, Workshop or REV assets here.
- Do not promote temporary, generated, rejected or founder-unreviewed imagery.
- Any modified asset receives a new version, path, SHA-256 and founder approval record.

These authorities protect the accepted visual direction. They do not authorize a later production change without an exact page/data/interaction Build Contract. Only canonical repository paths can carry authority.
