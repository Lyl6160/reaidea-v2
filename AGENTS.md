### Session continuity and Founder Control System gate

`AGENTS.md` is the enforcement gateway, not product authority. The Founder Product Constitution remains durable product authority, the Security Engineering Standard remains mandatory, and `architecture/REAIDEA_FOUNDER_CONTROL_SYSTEM_2026-08-27.md` controls live working process.

Every session follows this LOGIN/RESUME order:

`AGENTS.md` → `CONTEXT_START_HERE.md` → `CURRENT_CONSTRUCTION_STATE.md` → `FOUNDER_PRODUCT_CONSTITUTION.md` and `SECURITY_ENGINEERING_STANDARD.md` → `architecture/FOUNDER_VISUAL_LOCK_STANDARD.md` and its manifest → exact approved Visual Authority → accepted architecture/runtime contract and active Build Contract → `continuity/ACTIVE_HANDOFF.md` → historical evidence only as required

1. Read `CONTEXT_START_HERE.md` as navigation only.
2. Read the plain-text `CURRENT WORK` block at the top of `CURRENT_CONSTRUCTION_STATE.md`. It is the sole live reference, phase, iteration, checklist and stop gate.
3. Read `FOUNDER_PRODUCT_CONSTITUTION.md`, `SECURITY_ENGINEERING_STANDARD.md` and the Founder Control System.
4. For any visual task, read `architecture/FOUNDER_VISUAL_LOCK_STANDARD.md`, run `node scripts/verify-founder-visual-lock.mjs`, then read only the relevant Flight Plan, page register, visual register, exact Visual Page Blueprint, lane, supersession/decision and runtime-contract records required by the current reference.
5. Read the founder-approved active Build Contract named by `CURRENT WORK`.
6. Read `continuity/ACTIVE_HANDOFF.md` and stop if it does not copy current state exactly.
7. Verify branch, local HEAD, configured upstream, ahead/behind without fetching, tracked and untracked worktree paths, and index.
8. Create `continuity/daily/YYYY-MM-DD/` from the templates if today's folder is absent.

Historical journals, daily logs, handovers and construction sections are evidence only. Wording such as “current”, “active”, “next action” or “proceed” inside them cannot authorize work when it differs from `CURRENT WORK`.

If the current reference, exact founder authorization, Build Contract, required visual authority, allowed paths or stop conditions are missing or conflict, remain read-only. Before modifying Next.js code, also read the relevant guide under `node_modules/next/dist/docs/`.

Before action, account for all ten Founder Control System items: current reference/phase/iteration; exact founder authorization; branch/HEAD/upstream/index; tracked/untracked paths; required starting state; exact allowed files; exact prohibited files/protected foundations; visual references/hashes; tests/walkthrough; stop conditions.

Present that accounting to the founder as exactly one short six-line starting summary:

1. Current reference, phase, iteration and checkpoint.
2. Active lane and exact founder authorization.
3. Baseline HEAD, upstream, parity and index.
4. Tracked/untracked worktree and required starting state.
5. Allowed/prohibited paths, protected invariants and visual hashes.

- Never change production presentation without a founder-approved Visual Page Blueprint and exact screen/data/interaction Build Contract.

- Use only these live visual-status phrases: `TECHNICALLY VERIFIED — AWAITING FOUNDER VISUAL WALKTHROUGH`, `FOUNDER REJECTED — REMAIN INSIDE CURRENT CATEGORY`, and `FOUNDER VISUALLY APPROVED — DOCUMENTATION CHECKPOINT REQUIRED`.
- Do not advance phase, iteration or REV-FIX reference automatically.

### Hard Founder Visual Lock

- A founder-approved image is immutable authority, not inspiration. Never regenerate, redraw, rescan, restyle, recolour, recompose, crop, replace, patch over or silently reinterpret it.
- `architecture/FOUNDER_VISUAL_LOCK_STANDARD.md` and `visual-authority/FOUNDER_VISUAL_LOCK_MANIFEST.json` are mandatory visual-process controls.
- Run `node scripts/verify-founder-visual-lock.mjs` at visual-session login, before any approval image, before production implementation, after implementation and at handover. Stop on any mismatch.
- A flattened approved screen containing controls from one state cannot be reused as the background for another state. If clean source layers cannot preserve every approved pixel outside the requested change, stop and ask the founder.
- KIS means one screen, one state, one requested change, one complete standalone preview and one founder decision. Add nothing else.
- Production presentation cannot change until the founder has approved the exact complete next-state image and that file, state and SHA-256 are registered.
- One founder rejection ends the attempt. Mark it rejected and stop; do not patch, iterate or generate another version without new exact founder direction.
- Rejected visuals and code remain historical evidence only. They can never be authority, inspiration, fallback or tomorrow's starting point.
- Technical verification is not visual approval. Stop for the founder's live walkthrough and do not advance the category automatically.

### Sign-off

Before ending a working day or handing off:

1. Update today's `DAILY_LOG.md` and `EVIDENCE_INDEX.md`.
2. Replace `continuity/ACTIVE_HANDOFF.md` with current truth.
3. Update `continuity/DAILY_INDEX.md`.
4. Record branch, local HEAD, remote-tracking SHA, ahead/behind and the GitHub repository reference.
5. Provide the short `REV HANDOFF` defined by `architecture/AGENT_HANDOVER_STANDARD.md`.
6. Commit or push daily records only with founder authorization or an accepted checkpoint.
7. Never stage unrelated, rejected or unfinished work.

### Mandatory security engineering guard

Before material architecture or implementation work, read and comply with
`SECURITY_ENGINEERING_STANDARD.md`. Perform a lightweight threat assessment,
escalate unresolved HIGH or CRITICAL risks, and add proportionate negative
security tests. Do not claim a change is production-ready or security-verified
without evidence. Implementation reports must state security posture, threats
considered, controls, security tests, open risks, residual risk, and production
requirements.
