## 3. Four permanent project records

### `CONTEXT_START_HERE.md`

Navigation only: authority order, current branch family, protected foundations and links to the live construction state, visual authority and active handoff. It changes rarely.

### `CURRENT_CONSTRUCTION_STATE.md`

The one live Founder Build Board. Its top must state current reference, phase, iteration, controlled status, exact allowed and prohibited files, exact founder gate, locked next reference, branch/HEAD/parity and latest applicable visual hashes. No agent may start work outside the current authorized reference.

### Visual authority

Every accepted visual records its reference, path, dimensions, SHA-256, state shown, scope controlled, exclusions, founder approval wording and rejected predecessors. An image described only as approved without a state and hash is insufficient authority.

### `continuity/ACTIVE_HANDOFF.md`

The next-day restart record. It copies but cannot change the current reference, phase, approvals, defects, exact next action, exact founder gate, protected files, branch, HEAD, parity and worktree. If it conflicts with the construction state, the construction state wins and the handoff must be corrected before work.

## 4. Five phases for every build category

### Phase 1 — Contract

- Inspect read-only.
- Confirm the required starting state.
- Identify the exact defect and visual authority.
- Propose exact files and tests.
- Stop for founder authorization.

### Phase 2 — Build

- Change only authorized files.
- Do not redesign approved earlier categories.
- Do not advance automatically.
- Stop when the slice is ready.

### Phase 3 — Engineering verification

- Build and focused tests pass.
- Exact file boundary and runtime invariants pass.
- Git diff, index and worktree are accounted for.
- No test data is mistaken for blank Home.

### Phase 4 — Founder walkthrough

- The founder uses the real running page from the required state.
- Desktop, 1100×800 and 390×844 are reviewed where applicable.
- Live animation, failure, refresh and reduced motion are reviewed where applicable.
- The founder approves or rejects.
- Rejection remains in the same category as a new iteration.

### Phase 5 — Documentation checkpoint

Only after founder approval: record evidence/hashes, tests, closed defects, limitations and deferrals; update construction state and handoff; propose the exact commit boundary; commit or push only with founder authorization; keep the next category locked until separately authorized.

## 5. Founder visual authority

Automated checks and agent inspection may verify application truth, persistence, routing, accessibility structure, responsive dimensions, file boundaries, test results, errors, viewer/Canvas ownership and whether an effect runs. They cannot grant visual approval.

Only the founder can approve visual quality, composition, atmosphere, REV's appearance, electrical feeling, animation pacing, Creation Theatre engagement, wireframe professionalism, final 3D quality or journey readiness after viewing the real running experience.

The constant walkthrough rhythm is: one bounded problem; technical checks; real live founder walkthrough; approve or record defects; remain in the same category until accepted; document/checkpoint; lock the accepted foundation; prepare but do not begin the next category.

Screenshots are supporting evidence. Motion, interaction, responsiveness, persistence, refresh and timing require founder review of the live application.

After approval, accepted appearance and behavior are protected. Later work cannot silently redesign them. An unavoidable impact requires an explicit change request and a new founder walkthrough.

Required visual status wording:

- `TECHNICALLY VERIFIED — AWAITING FOUNDER VISUAL WALKTHROUGH`
- `FOUNDER REJECTED — REMAIN INSIDE CURRENT CATEGORY`
- `FOUNDER VISUALLY APPROVED — DOCUMENTATION CHECKPOINT REQUIRED`
